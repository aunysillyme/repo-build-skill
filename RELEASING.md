# Releasing and maintenance

## What and why

A release turns a reviewed source tag into one tested npm tarball, publishes that artifact and verifies its registry listing.
The proof and health workflows keep evidence and public metadata current between releases.
The owner authorizes publication and visibility changes; the AI prepares the artifacts and checks.

Our own tools and concepts are named with the aun- prefix; internal names never ship, and the INTERNAL_TERMS test enforces it.

## Sources of truth

- `package.json` defines the package name, command, runtime, version and published allowlist.
- `.repo-build/facts.json` defines public copy, install commands and topics.
- `skills/repo-build-skill/manifest.json` defines routes, manual gates, budgets and asset hashes.
- Rule objects in `src/check/rules/` define automated checks and generated teaching tables.
- `.github/workflows/` defines the automation actually run by GitHub.
- `proof/results.json` holds dated measurements of this package.
- `.repo-build/set.json`, its lock and renderer define the local set blocks.

## Dependencies and authority

The local commands use the Node runtime declared in `package.json` and npm.
Type checking uses the exact development dependency in the lockfile.
GitHub Actions supplies the pinned actions and the publish job's short-lived OIDC identity.
The release runner selects Node 24 and npm 12.2.0 as declared in `release.yml`; re-check registry floors on the release date.
The package must exist on npm and its trust record must name this repository and `release.yml` exactly.
The first publish and Trusted Publisher configuration are owner's actions at npmjs.com.
The repository must be public when npm provenance is requested.
The public settings targets and read-back live in [REPO_SETTINGS.md](REPO_SETTINGS.md).

## Prepare the version

Record the current published tag and tarball integrity as the rollback reference before changing a release.
Registry versions are immutable: recovery publishes a corrected version; deprecation and dist-tag changes need the owner's authorization.
Choose a Semantic Versioning increment and edit the changelog from Unreleased to a dated release section.

Update the version sites together:

- `package.json`: `version`.
- `package-lock.json`: root `version` and `packages[""].version`.
- `.claude-plugin/plugin.json`: `version`.
- `.claude-plugin/marketplace.json`: `metadata.version` and any declared plugin version.
- `skills/repo-build-skill/manifest.json`: `packageVersion`.
- `skills/repo-build-skill/SKILL.md`: `metadata.version`.

Run `node scripts/build.mjs --rehash <changed-asset-path>`, with paths relative to the skill folder.
List each asset changed, including stage files and SKILL.md; the generator owns gate tables.
Run `npm run build`, `npm test`, `npm run check` and `npm run typecheck` on the final source.
Use `node scripts/build.mjs --check` to verify generated bytes.
Refresh deterministic proof with `npm run proof` after content is final.
Use [EVALUATION.md](docs/EVALUATION.md) for outcome rows before their expiry.
Run `node scripts/showcase.mjs` to write stage receipts, then review their manual statuses.

Apply aun-cross-review: one independent review by a different model family before release, or WAIVED with owner, reason and date.
Resolve reproduced findings and replay the acceptance checks against the final artifact.
Run the privacy check with the maintainer's private lists and `--history` before publication.
Keep those lists gitignored and out of release artifacts.

## release.yml

**Trigger:** a pushed tag matching `v*`.
A push to main runs repository checks; the tag is the publication trigger.

**Invocation chain:** the verify job (read-only token) checks out the tag, compares it with `package.json`, runs tests, checks generated files, self-checks and type-checks.
It then packs once and installs that tarball in a temporary consumer project, runs help, dry-run install, install and uninstall against the installed binary and checks the installed target was removed.
It uploads that tarball as an artifact.
The publish job waits for verification, downloads the artifact, selects the publishing CLI and publishes that exact file with provenance.
Only the publish job has `id-token: write`, and it runs no install, build or package script; checkout keeps persisted credentials disabled.

**Reads:** tagged source, package and lockfile, skill manifests, tests and the npm trust identity.
**Writes:** the npm version, tarball, dist-tag and provenance; GitHub run logs.
It creates no GitHub release page; the maintainer creates that page after registry verification.

**Closed loop:** job failures stop the publish path and appear in Actions.
Notification delivery depends on the account's GitHub settings and remains UNVERIFIED until tested.
A green job proves that job's result; the registry query is the release completion check.
Nothing in this workflow polls the registry after publish.

## First publish and normal release

The owner completes the initial `npm publish <reviewed-tarball> --access public` with their account verification.
Then configure Trusted Publisher on the [npm package settings](https://www.npmjs.com/package/repo-build-skill/access), naming owner `aunysillyme`, repository `repo-build-skill` and workflow `release.yml`.
Re-read npm's official trusted-publishing documentation that day and read back the saved trust record.
Changing the workflow filename requires re-creating that identity.
A similar-name E403 at the first publish goes to the owner with the scoped fallback `@aunysillyme/repo-build-skill`; update all name sites before retrying.

For a reviewed version `X.Y.Z`, the maintainer performs the authorized release:

```sh
git tag -a vX.Y.Z -m "X.Y.Z: release summary"
git push origin vX.Y.Z
gh run list --workflow release.yml --limit 1
gh run watch RUN_ID --exit-status
bash scripts/verify-registry.sh vX.Y.Z
```

Verify the named version, attestation, README, description, bin, funding and homepage against the tag.
Allow registry propagation and retain query output as the receipt.
Try `npx --yes repo-build-skill@X.Y.Z --help` in a fresh directory outside this checkout.
Create the release page with `gh release create vX.Y.Z --notes-file RELEASE_NOTES.md`, using the reviewed changelog section.
Every user-facing change, including copy, reaches the registry through a release.

Record the terminal demo from the published package in a fresh directory outside this repository.
Use only commands that exist and numbers from the proof file.
The owner approves trailer keyframes before a trailer is rendered.

## proof.yml

**Trigger:** the schedule in `.github/workflows/proof.yml`, or manual dispatch.
**Invocation chain:** checkout, setup Node, run `node scripts/proof.mjs --deterministic`, run the proof test and propose one refresh pull request.
**Dependencies:** npm packing, local checker code and the Actions token's contents and pull-request permissions.
**Reads:** published allowlist, local source, the tiny-tool fixture and existing proof rows.
**Writes:** deterministic rows in `proof/results.json`, an automation branch and one pull request.
The workflow preserves model evaluation rows and holds no model key.
It updates the proof data only; after review the maintainer refreshes the README table from unexpired rows, including measured and expires dates.

**Closed loop:** a maintainer reviews the proposed data and runs required checks before merging.
A pull request opened by the Actions token does not start another Actions run automatically.
Maintainer-run outcome evaluations refresh the model-dependent rows before expiry.
Expired proof warns and is omitted from displayed claims; expiry never blocks a release.

**Hand verification:** run `node scripts/proof.mjs --deterministic`, inspect the changed rows and run `node --test test/proof.test.mjs`.
Each row must name its command, package version, measured date and expiry.
Runtime results belong to the measured machine; package size changes when the contents change.

## repo-health.yml

**Trigger:** the schedule in `.github/workflows/repo-health.yml`, or manual dispatch.
**Invocation chain:** checkout, setup Node, run `node scripts/repo-health.mjs`.
This is aun-repo-health: public parity checks that open, update or close one health issue.
**Dependencies:** GitHub and registry reachability, a valid homepage and the Actions token's issues permission.
**Reads:** facts, package metadata, GitHub About, registry data, llms.txt and the local set lock.
**Writes:** one `repo-health` issue while findings remain; closes open health issues after a clean observation.
It neither fetches nor synchronizes the canonical set source in CI.
The maintainer refreshes set data with `npx repo-build-skill set sync` and reviews the diff.

**Closed loop:** the issue carries current findings and the reproduce command.
The next scheduled or manual run observes the repair and closes the issue after parity is restored.
An unreachable service remains a finding that the maintainer can reproduce.
Nothing automatically merges, publishes or changes remote settings.

**Hand verification:** run `node scripts/repo-health.mjs --check-only` to inspect findings without issue writes.
Use an authorized environment with `GITHUB_REPOSITORY` and the Actions token for issue maintenance.
Keep credentials outside command arguments and logs.

## Failure handling

| Observation | Action |
|---|---|
| Tag differs from package version | Fix the version sites and create the intended tag through the authorized release procedure. |
| Trust exchange fails | Compare the exact repository, workflow filename and environment with the npm trust record. |
| Registry still serves earlier data | Query the explicit version and poll the listing before declaring completion. |
| Packed install or uninstall fails | Keep publication blocked, preserve the fixture evidence and fix the artifact. |
| Generated output drifts | Change its source and rerun the build and affected asset rehash. |
| Set renderer hash drifts | Maintainer runs set sync and reviews the lock and renderer together. |
| Health request fails | Retain UNVERIFIED evidence, inspect service reachability and rerun the read-only probe. |
| Proof refresh PR fails | Inspect the workflow log, reproduce deterministic measurements locally and repair the source. |

Report breakage through the [bug form](https://github.com/aunysillyme/repo-build-skill/issues/new/choose) with version, exact command and sanitized output.
Security issues use [private reporting](SECURITY.md).
Hosted automation and notification delivery stay UNVERIFIED until observed in the actual repository.
